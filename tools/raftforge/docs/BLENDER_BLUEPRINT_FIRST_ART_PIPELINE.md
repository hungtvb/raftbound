# RAFTFORGE — blueprint-first Blender art production

Adapted from the **workflow pattern** in the supplied Japanese temple reconstruction
screenshot. The screenshot describes a third-party proposal, **not a verified
installed skill or software stack**. We reuse production discipline, not its
vendor names or unsupported promises of tools.

## Stage 00–01 — Lock one source of truth

**Architecture / buildings**: dimensional BIM/IFC/CSG models and metric CAD
plans are authoritative. Exported CAD plans, BIM geometry, world Z-datums
and UV maps should be derived from the same data where possible. A scanned
4-angle photo contact sheet is not a substitute for dimensional plans.
Coordinate systems, thicknesses, levels and section cuts are recorded.

**RAFTBOUND characters**: the authoritative inputs are
`compact_sailor_blueprint.json` and a pinned, licensed 65-joint CC0 source
GLB. All poseable garment meshes, joint rest positions and accessories must
be changed in **Blender**, re-exported and read back; never fix the appearance
by stretching a PNG or only fitting a GLB root. Lock dimensions and the original
model hash, model orientation, character/foundation scale and poly budget.
For the current candidate:

- Target nominal upright height **1.66 m**; 2 m raft tile gives a grounded
  scale, but that alone does not certify appearance in gameplay.
- Head-width-to-height **at least 0.115**; shoulder-span-to-height
  **at most 0.22**; these are project review bounds, *not measured values of
  copyrighted Raft game character designs*.
- CC0 base rig, clothing and prop attachments are rebuilt as actual meshes.
- Never claim that a standalone AI image is the exported character GLB.

**Gate**: `stylize_proportions.py` writes `proportions.json` from true
rest geometry. `reference_lock.py` refuses to approve candidates outside the
locked contract or with changed joint counts.

## Stage 02 — Four-angle reference sheet (2×2)

Temple architecture may use 4 photorealistic image references for architectural
orientation (north/east/south/west), but those images are *supportive concepts*,
not literal structural ground truth. Their geometry must be reconciled with
BIM/CAD blueprints.

For RAFTBOUND generate **actual GLB evidence** at FRONT / THREE-QUARTER /
BACK / TOP. Do it for baseline **and** candidate with the **same camera
bounds**. Per-model auto framing is misleading: it hides if a resculpt
really became shorter. Publish:

- `reference_2x2_before.png`
- `reference_2x2_after.png`
- `before_vs_after_matrix.png`
- `candidate_gameplay_120px.png` (small reviewer thumbnail,
  **not** a screenshot of the actual game)

The contract report pins SHA-256 of both GLBs, the blueprint and dimensions.
A four-angle reference generated by an image model is allowed only as **labeled
concept**, not fake geometry or real Blender render evidence.

## Stage 03 — Four independent specialists and master reviewer

| Domain | Owner | Required output | Rejection criteria |
|---|---|---|---|
| Silhouette, blueprint | Art direction | Locked shape ratios, camera references, visible face | Bulky body, hidden eyes, unreadable head |
| Mesh + skeletal topology | Blender modeler | Deformed GLB, seams, bones, weights, attachments | Jagged hems, lost rig, floating equipment |
| PBR + UV/material | Surfacing artist | Actual exported glTF material/texture tests | White material, missing atlas, fake texture claims |
| Animation + in-game | Runtime engineer | Real idle/walk/cast GLB clips and game-camera footage | T-pose, clipping, mismatched tool grip, 17/65-joint mismatch |

The **master reviewer** checks hashes and A/B images, asks for one
measurable correction at a time, and blocks release if any human art dimension
is under 4/5. Parallel work is optional: four *roles* do not require four
paid AI agents, four API keys or a special "Gemini 4 Argon" backend.

**Editing rule**: a specialist changes only their owned artifacts; modifying
the blueprint requires a new revision and review. At most **three candidate
variants** per iteration; reject early, before expensive shader or rig work.

## Stage 04 — Full scene, sections and motion evidence

Architecture: use real Blender Cycles/Eevee camera perspectives,
orthographic elevations, **section A–A**, material swatches and dimensions.
Only state a BMesh section cut was made if a script actually created it.

Character: render a front/hero/rear/top turnaround and in-game-size
thumbnail. Then use Blender deformation and **Three.js GLTFLoader +
AnimationMixer** to play idle/walk/cast from the current game timeline.
A static screenshot does not prove a skin moves correctly. A numerical
nearest-point clearance cannot prove there are no cloth intersections.

## Stage 05 — Progression matrix & human acceptance

The matrix places BEFORE and AFTER under the same camera, lighting and model
origin. A JSON report separates technical PASS from **art PENDING**.

**Reject immediately** if proportions drift outside the locked blueprint,
there are missing joints/materials/meshes, glTF fails to load, three animation
clips are absent, or screenshot color is missing. **Art signoff** separately
requires silhouette, face, hands, clothing, gameplay readability and
animation deformation each >=4/5 with real reviewer notes. The final live
RAFTBOUND game has a 17-bone renderer; 65-bone integration is still blocked
until the actual runtime is upgraded and tested.

## Reproducible A14 command

```bash
PYTHONPATH=tools/raftforge xvfb-run -a python -m character_lab.reference_lock \
  --baseline qa-character-a14/sailor-costume-game-oriented.glb \
  --candidate qa-character-a14/sailor-compact-game-oriented.glb \
  --proportions qa-character-a14/proportions.json \
  --blueprint tools/raftforge/character_lab/compact_sailor_blueprint.json \
  --out qa-character-a14/reference-lock
```

Dependencies: free `numpy`, `trimesh`, `pillow`, `vtk`; no required
Nano Banana, Gemini or paid render service.

**Not in scope**: programmatically creating arbitrary temples through OpenBIM
or extracting proprietary tools. For temple production, IFC/CAD source
ingestion is an independent architecture-specific implementation project.
